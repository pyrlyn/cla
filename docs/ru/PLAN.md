# pyrlyn/cla: план

Статус: action (5.2) реализован; учётные данные, переключение infra и включение (5.3–5.6) ещё
впереди. Написан 2026-10-03.
Это перевод. Источник истины — английский [`PLAN.md`](../../PLAN.md); при расхождении действует
английский текст. Другие переводы: [украинский](../uk/PLAN.md).

`pyrlyn/cla` — небольшой GitHub Action, принадлежащий организации, который проверяет в
pull request'ах подписание Contributor License Agreement (лицензионного соглашения участника,
далее CLA) pyrlyn. Он заменит CLA Assistant Lite (`contributor-assistant/github-action`), который
сейчас оборачивает `pyrlyn/ci` и который был архивирован 2026-03-23.

## 0. Цели и что не входит в задачу

Цели:

1. Каждый, чья работа есть в pull request, «покрыт»: подписал текущую версию CLA, является
   участником организации `pyrlyn` или это бот из allowlist.
2. Подписание по-прежнему — комментарий в pull request с фиксированной фразой, как описано в
   разделе 11 `CLA.md`.
3. Одна подпись действует для всех репозиториев pyrlyn. Подписи хранятся в репозитории, которым
   владеем мы.
4. Понятная, стабильная обязательная проверка (required check), которую можно указать в rulesets,
   и один комментарий бота, где точно сказано, чего не хватает и как это исправить.
5. Версии CLA: новая версия может потребовать подписать соглашение заново.
6. Безопасность на `pull_request_target`: код из pull request никогда не checkout'ится и не
   запускается.

Не входит: веб-интерфейс или страница «Sign in with GitHub», корпоративные CLA (компания
подписывает за своих сотрудников; решается обращением к Лицензиару, `CLA.md` 11.4), DCO sign-off,
другие платформы, кроме GitHub.

Для плана изучены две кодовые базы:

- **Upstream** `contributor-assistant/github-action`, архивирован, последний коммит `58daaf8`
  (2026-03-23). `pyrlyn/ci` закрепляет тег `v2.6.1` = `ca4a40a7d1004f18d9960b404b97e5f30a505a08`.
  Лицензия Apache-2.0.
- **Форк** `iainmcgin/cla-github-action`, `v3.2.0` = `0d27e5a16278d4adb6b0c4b92f08ad27b0a21dc8`
  (2026-06-17). Apache-2.0. Ответвился от `58daaf8`; изменения описаны в его `CHANGELOG.md`.

### 1.1 Процесс подписания

- Точка входа `src/main.ts`: на событии `closed` только блокирует обсуждение pull request
  (`lockPullRequest()`); в остальных случаях вызывает `setupClaCheck()`.
- `src/setupClaCheck.ts`: собирает авторов коммитов, убирает тех, кто в allowlist, читает файл
  подписей, делит людей на `signed` / `notSigned` / `unknown` (нет аккаунта GitHub), обновляет
  комментарий бота, записывает новые подписи, затем либо роняет job, либо перезапускает последний
  упавший запуск.
- `src/graphql.ts`: авторы берутся из GraphQL-запроса `pullRequest.commits`, для каждого коммита
  `author.user`, иначе `committer.user`. Пользователь `41898282` (`github-actions[bot]`)
  отбрасывается всегда. Upstream читает только первые 100 коммитов (без пагинации).
- `src/pullrequest/signatureComment.ts`: получает комментарии pull request и считает комментарий
  подписью, если он совпадает с фразой. Upstream использует нестрогое регулярное выражение
  `^.*i have read the cla document and i hereby sign the cla.*$` по тексту в нижнем регистре и
  читает только первые 30 комментариев (без пагинации). Для каждого подписавшего сохраняются
  `name`, `id`, `comment_id`, `created_at`, `repoId`, `pullRequestNo`. Комментарии
  `github-actions[bot]` никогда не засчитываются.
- `src/shared/pr-sign-comment.ts`: фраза по умолчанию
  `I have read the CLA Document and I hereby sign the CLA` (input `custom-pr-sign-comment`).
- `src/pullrequest/pullRequestComment.ts` + `pullRequestCommentContent.ts`: бот создаёт один
  комментарий и дальше редактирует его на месте; в нём список неподписавших и фраза, которую надо
  опубликовать.
- Перепроверка: вызывающий workflow фильтрует события `issue_comment`, так что запуск начинают
  только `recheck` или сама фраза.
- `src/pullRerunRunner.ts`: запуск по комментарию идёт на событии `issue_comment`, поэтому его
  результат не привязан к head-коммиту pull request. Поэтому action ищет собственный workflow
  **по имени** (`context.workflow`), получает запуски `pull_request_target` на head-ветке и
  перезапускает последний, если тот упал. Для этого нужно `actions: write`; механизм ломается,
  когда у двух workflow одинаковое имя («Unable to locate this workflow's ID»), и сопоставляет
  head-ветку только по имени (ветка форка с именем `main` может совпасть с чужими запусками).

### 1.2 Хранение

- `src/persistence/persistence.ts`: один JSON-файл `{"signedContributors": [...]}`, который
  читается и записывается через contents API (`repos.getContent` / `createOrUpdateFileContents`)
  в ветке из input `branch` по пути `path-to-signatures`.
- Тот же репозиторий: используется `GITHUB_TOKEN`, поэтому job нужно `contents: write`, а ветка
  не должна быть защищена. Удалённый репозиторий (`remote-organization-name` /
  `remote-repository-name`): используется `PERSONAL_ACCESS_TOKEN` (`src/octokit.ts`); без него
  запуск падает с «Please add a personal access token».
- Запись использует `sha` файла, полученный при чтении; две подписи в один момент конфликтуют, и
  один из запусков падает («Could not update the JSON file»). Повтора нет.
- Ошибка в upstream: `src/setupClaCheck.ts` сравнивает `error.status === "404"` (строку) с
  числовым статусом, поэтому ветка «создать файл при первом запуске» никогда не выполняется. С
  `v2.6.1` отсутствующий `cla.json` заканчивается ошибкой «Could not retrieve repository contents.
  Status: 404». В форке это исправлено (`c5254b2`). В `pyrlyn/ci` `docs/cla.md` сейчас
  написано, что action создаёт файл сам; с закреплённой версией это неверно.

### 1.3 Логика проверки

- Результат = результат job: `core.setFailed()` делает job красным. Statuses API нигде не
  вызывается, хотя в документированных правах есть `statuses: write`.
- Allowlist (`src/checkAllowList.ts`): логины через запятую, шаблон `*` превращается в регулярное
  выражение. Upstream проверяет только логин; форк проверяет ещё и email коммита (`73f6929`).
- Блокировка pull request (`src/pullrequest/pullRequestLock.ts`): после `closed` обсуждение
  блокируется, чтобы комментарии-подписи нельзя было отредактировать. Upstream блокирует при
  **любом** закрытии, в том числе без merge; заново открытый pull request тогда не может получить
  комментарий бота. Исправлено в форке `v3.1.0` (`30dab6b`): блокировать только после merge,
  разблокировать при `reopened`.
- Идентичность: поля автора в git не аутентифицированы. Любой может создать коммиты с чужим email
  (например, бота из allowlist или уже подписавшего участника); GitHub сопоставит email с этим
  аккаунтом, и upstream засчитает этот аккаунт. Форк в `v3.0.0` добавляет к проверяемым людям
  автора pull request и трейлеры `Co-authored-by:` (`src/shared/coAuthors.ts`) и падает, когда
  автор pull request не является автором ни одного коммита (`require-opener-as-author`, по
  умолчанию `true`).
- Форк `v3.2.0` (`1f440bd`): фраза должна стоять на отдельной строке, регистр не важен, `.`/`!`
  в конце игнорируются, цитируемые (`>`) строки не засчитываются, допускается совсем немного
  дополнительного текста.
- Среда выполнения: `action.yml` upstream объявляет `node20`, форк — `node24`. GitHub запускает
  JavaScript actions на Node 24 с 2026-09-23.

### 1.4 Безопасность `pull_request_target`

Оба проекта документируют связку `pull_request_target` + `issue_comment`. `pull_request_target`
запускает workflow из **базовой** ветки с токеном на запись и секретами, в том числе для
pull request'ов из форков. Это безопасно, только пока workflow никогда не checkout'ит и не
выполняет код из pull request и никогда не подставляет контролируемый атакующим текст (заголовки,
описания, комментарии, имена веток) в скрипты `run:`. Ни один из двух actions код не checkout'ит;
оба читают данные pull request только через API.

### 1.5 Что берём

| Идея | Источник | Решение |
| --- | --- | --- |
| Подпись комментарием в PR, закреплённый комментарий бота, `recheck` | upstream | оставляем |
| JSON в отдельном приватном репозитории | upstream | оставляем, новая схема |

`NOTICE`. Лицензия самого `pyrlyn/cla`: Apache-2.0 (решение за Иваном; так проще переносить код).

## 2. Требования pyrlyn

### 2.1 Кто считается покрытым

Человек покрыт, если выполняется любое из условий; проверяются в таком порядке:

1. **Участник организации** `pyrlyn` (проходит автоматически, без подписи). Input
   `members-pass: true`.
2. **Бот из allowlist**, сопоставление по числовому ID пользователя и логину, никогда по email.
3. **Подписал** версию CLA, которая требуется сейчас.

Проверяются: автор pull request, каждый автор коммита, каждый коммиттер, который является
пользователем GitHub, кроме `web-flow` (ID `19864447`), и каждый трейлер `Co-authored-by:`. Email
автора, не привязанный к аккаунту GitHub, считается «неизвестным»: подписать с ним нельзя, проверка
остаётся красной, а комментарий объясняет, как привязать email или переписать коммиты.

Защита от подмены (из форка): если автор pull request не является автором или соавтором ни одного
коммита, проверка падает, если только он не участник организации. Посторонний поэтому не сможет
пройти проверку, приписав коммиты боту из allowlist или тому, кто уже подписал.

Юридическое замечание для Ивана: сейчас единственный участник — `listepo` (правообладатель).
Будущий участник, который не Иван, будет вносить вклад без подписи. Либо участники подписывают
отдельное соглашение, либо ставим `members-pass: false`. Членство проверяется в момент проверки и
не сохраняется.

### 2.2 Проверка членства

`GITHUB_TOKEN` не видит скрытое (private) членство в организации: это installation token без
организационного права «Members». Тогда `GET /orgs/pyrlyn/members/{user}` показывает скрытых
участников как не участников. Сейчас `listepo` — скрытый участник (`/orgs/pyrlyn/public_members`
пуст). `author_association` в данных события тоже не надёжный признак членства.

| Вариант | Как | Плюсы | Минусы |
| --- | --- | --- | --- |
| A. **GitHub App** `pyrlyn-cla` (рекомендуется) | приложение организации, право организации **Members: read**, право репозитория **Contents: read and write**, установлено только на `pyrlyn/cla-signatures`; токен выпускается на каждый запуск через `actions/create-github-app-token` | одна учётная запись и для членства, и для хранения; без срока действия; доступ к одному репозиторию; коммиты подписей от имени бота | нужно создать и установить приложение; два секрета (`CLA_APP_ID`, `CLA_APP_PRIVATE_KEY`) |
| B. Публичное членство | каждый участник делает членство публичным; проверка `GET /orgs/pyrlyn/public_members/{user}` с `GITHUB_TOKEN` | для этой части не нужен секрет | зависит от каждого участника; того, кто скрыл членство, попросят подписать |
| C. PAT организации | fine-grained PAT, владелец ресурса `pyrlyn`, право организации **Members: read** (+ Contents на `cla-signatures`) | быстро | привязан к аккаунту Ивана, истекает, нужно менять |
| D. Статический список | участники перечислены в `allowlist` | без вызова API | устаревает; по сути тот же allowlist |

План: реализовать A, поддержать C через тот же input (подойдёт любой токен с таким доступом), B
оставить запасным вариантом, если токен не передан. Если членство прочитать нельзя (403 / нет
токена), человек считается не участником, а в комментарии сказано, что членство проверить не
удалось. При ошибке проверка никогда молча не проходит.

### 2.3 Allowlist ботов

Список по умолчанию, по логину; числовой ID определяется во время запуска и сравнивается:

- `dependabot[bot]` (`49699333`), `github-actions[bot]` (`41898282`), `renovate[bot]`.
- Бот приложения `pyrlyn-cla` и любые другие приложения pyrlyn, добавленные позже.

Шаблоны разрешены только для логинов, заканчивающихся на `[bot]`, и задаются явно. Боты не
подписывают. Бот покрыт только как автор коммита; бот из allowlist в роли автора pull request с
посторонними авторами коммитов этих авторов не покрывает.

### 2.4 Текст CLA и версии

- Текст: `pyrlyn/ci` `CLA.md` «Version 1.0 (draft)» (английский, канонический) и `CLA.ru.md`
  (русский перевод). Раздел 11 описывает подписание фразой
  `I have read the CLA Document and I hereby sign the CLA`, сохраняемые данные (логин, числовой
  ID, ID и время комментария, репозиторий и pull request) и то, что одна подпись действует для
  всех проектов. Раздел 12.2: новая версия применяется к вкладам, сделанным после того, как
  участник её принял.
- До запуска в п. 11.1 `CLA.md` и `CLA.ru.md` нужно убрать упоминание «CLA Assistant Lite»
  (достаточно «автоматическая проверка»). Текст ещё черновик, поэтому новая версия не нужна.
  Опционально: украинский перевод `CLA.uk.md` (его нет).
- Inputs версии: `cla-version` (например, `1.0`), `document-url`, закреплённый на коммите
  `pyrlyn/ci` (`.../blob/<sha>/CLA.md`), и `document-sha256` (SHA-256 этого файла). Action
  сохраняет все три значения в каждой подписи.
- Повторное подписание: input `minimum-version`. Подпись с более низкой версией человека не
  покрывает; комментарий пишет «вы подписали версию X, теперь требуется версия Y» со ссылкой на
  новый текст. Повышение `minimum-version` — осознанный шаг. Сама по себе новая версия (12.2) не
  делает старые подписи недействительными для старых вкладов.
- Фраза остаётся такой, как в 11.1. Версия — та, на которую ссылался комментарий бота в момент
  подписания (11.2: «версия, ссылка на которую дана в сообщении проверки»).

### 2.5 Сообщения в pull request

Один закреплённый комментарий, который находится по скрытой метке `<!-- pyrlyn-cla -->`,
создаётся один раз и затем редактируется. На английском, со ссылками на `CLA.md` и `CLA.ru.md`.
Содержит:

- Таблицу всех проверенных: логин, причина (участник / бот / подписал v1.0 такого-то числа / нет
  подписи / неизвестный email / устаревшая версия).
- Точную фразу в блоке кода и указание «опубликуйте её отдельным новым комментарием».
- Подсказку про `recheck`; инструкцию для непривязанного email; предупреждение о подмене автора,
  если оно применимо.
- Когда все покрыты: одна короткая строка без `@`-упоминаний.

Commit status (context `pyrlyn/cla`), `description` до 140 символов (тексты на английском, как
они будут видны в GitHub):

- `success`: `All 3 contributors covered (1 member, 1 bot, 1 signed CLA 1.0)`
- `failure`: `CLA 1.0 signature missing: @alice, @bob. See the pull request comment.`
- `failure`: `Unknown commit email (not linked to GitHub): 1. See the comment.`
- `failure`: `PR opener @mallory is not an author of any commit.`
- `error`: `CLA check could not read signatures (HTTP 403). Maintainers: see the run log.`

`target_url` ведёт на комментарий бота. Job пишет step summary с той же таблицей.

## 3. Структура

### 3.1 Структура репозитория

```
action.yml            name, inputs, outputs; runs.using: node24, main: dist/index.js
src/main.ts           маршрутизация событий: pull_request_target, issue_comment, closed, reopened
src/config.ts         inputs, проверка (сразу падать при неверной конфигурации)
src/people.ts         автор PR, авторы, коммиттеры, Co-authored-by (GraphQL с пагинацией)
src/membership.ts     членство в организации, кэш на время запуска
src/allowlist.ts      боты по ID и логину
src/signing.ts        сопоставление фразы (строго, отдельная строка, без цитат)
src/store.ts          файл подписей: чтение, добавление, запись с повтором при 409
src/report.ts         закреплённый комментарий, commit status, step summary
src/lock.ts           блокировка после merge, разблокировка при reopen
tests/unit/           vitest, по файлу на модуль
tests/integration/    целые запуски против поддельного GitHub (записанные payload'ы, msw)
dist/index.js         бандл (ncc или esbuild), коммитится; CI падает, если он устарел
.github/workflows/    ci.yml (lint, typecheck, test, проверка dist), release.yml
NOTICE, LICENSE, README.md, PLAN.md, docs/ru, docs/uk
```

Node 24, TypeScript, `@actions/core`, `@actions/github`, `@octokit/plugin-retry`. Во время
выполнения никаких сетевых обращений, кроме GitHub API.

### 3.2 Inputs (первая версия)

`github-token` (по умолчанию `github.token`; комментарий, статус, блокировка), `cla-token`
(подписи + членство; токен приложения или PAT), `org` (`pyrlyn`), `members-pass` (`true`),
`allowlist`, `signatures-repository` (`pyrlyn/cla-signatures`), `signatures-branch` (`main`),
`signatures-path` (`signatures/cla.json`), `document-url`, `document-url-ru`, `cla-version`,
`document-sha256`, `minimum-version`, `sign-phrase`, `status-context` (`pyrlyn/cla`),
`lock-after-merge` (`true`), `require-opener-as-author` (`true`).
Outputs: `covered` (`true`/`false`), `missing` (JSON-список логинов).

### 3.3 Файл подписей

```json
{

  "signatures": [
    {
      "user": "alice", "user_id": 123,
      "cla_version": "1.0", "document_sha256": "…",
      "signed_at": "2026-10-10T12:00:00Z",
      "comment_id": 456, "comment_url": "https://github.com/pyrlyn/cox/pull/1#issuecomment-456",
      "repository": "pyrlyn/cox", "repository_id": 789, "pull_request": 1
    }
  ]
}
```

Только добавление; сопоставление по `user_id`, никогда по логину (логин можно переименовать).
Запись: прочитать, добавить, записать с прочитанным `sha`, при 409 перечитать и повторить (до 5
раз). Отсутствующий файл создаётся. Подписей пока нет, поэтому миграция формата Lite не нужна.

### 3.4 Хранение: отдельный репозиторий или ветка

| | `pyrlyn/cla-signatures` (приватный) | ветка в том же репозитории |
| --- | --- | --- |
| Токен | запись в один приватный репозиторий | `contents: write` на репозиторий с кодом |
| История | отдельная, не засоряет закрепления кода | коммиты подписей в каждом репозитории |
| Одна подпись на все репозитории | да | нет (по файлу на репозиторий) |
| Защита веток | незащищён только `main` там | незащищённая ветка в каждом репозитории с кодом |

Решение: `pyrlyn/cla-signatures`. Он уже существует (приватный, создан 2026-10-02) и **пуст**:
GitHub отвечает 409 «Git Repository is empty», поэтому нужен первый коммит (README), прежде чем
contents API сможет в него писать. Делать резервные копии (например, еженедельный
`git clone --mirror`).

### 3.5 События и переиспользуемый workflow

Action остаётся шагом внутри существующего переиспользуемого workflow `pyrlyn/ci`
`.github/workflows/cla.yml`; вызывающие репозитории сохраняют свой тонкий `cla.yml`:

- `pull_request_target`: `opened`, `synchronize`, `reopened`, `closed`.
- `issue_comment`: `created`, только для pull request'ов, когда текст содержит фразу или равен
  `recheck`.
- Запуск по комментарию сам ставит commit status на **head SHA** pull request. Это убирает логику
  перезапуска, `actions: write` и правило «имя workflow должно быть уникальным».
- Concurrency: `group: cla-${{ github.event.pull_request.number || github.event.issue.number }}`,
  `cancel-in-progress: false`.
- Никогда `actions/checkout`, никогда не запускать `npm`/скрипты из pull request, никаких
  `${{ … }}` с текстом события внутри `run:`. Action только вызывает API.
- Выключатель `vars.CLA_ENABLED == 'true'` остаётся.

Job зелёный, если action отработал; решение — это commit status. Красный job значит, что упал сам
action; тогда статус не ставится, и обязательная проверка блокирует merge (fail closed).

### 3.6 Имя обязательной проверки

Rulesets требуют status context **`pyrlyn/cla`** (а не имя job `cla / cla`). Его ставит
приложение `github-actions`; в ruleset можно закрепить этот источник (integration ID `15368`).

### 3.7 Релизы и закрепление

- Семантические версии `v1.0.0`, …, подписанные аннотированные теги, GitHub releases с
  описанием. Плавающий тег `v1` — только для удобства.
- Потребители закрепляют полный SHA коммита с комментарием `# v1.0.0` (как `pyrlyn/ci` уже
  делает для всех actions; это проверяет `action-pins.yml` в `infra`).
- CI на каждый PR: lint, typecheck, тесты, актуальность dist. Релизы только из `main`.
- Dependabot для npm и actions в `pyrlyn/cla`; Dependabot в `pyrlyn/ci` обновляет закрепление.

## 4. Секреты и права

Текущее состояние (проверено 2026-10-03): `gh secret list -o pyrlyn` показывает
`CARGO_REGISTRY_TOKEN`, `MACOS_CERTIFICATE`, `MACOS_CERTIFICATE_PWD`, `RELEASE_PLZ_TOKEN`.
**`CLA_SIGNATURES_TOKEN` не существует.** Переменных организации нет, то есть `CLA_ENABLED` на
уровне организации не задан.

| Учётные данные | Где | Доступ | Для чего |
| --- | --- | --- | --- |
| `github.token` | каждый запуск | права job ниже | комментарий бота, commit status, блокировка/разблокировка, чтение PR |
| `CLA_APP_ID`, `CLA_APP_PRIVATE_KEY` (вариант A) | секреты организации, выбранные репозитории | приложение: Members read на уровне организации; Contents read/write только на `cla-signatures` | членство, подписи |
| `CLA_SIGNATURES_TOKEN` (вариант C или старый Lite) | секрет организации, выбранные репозитории | fine-grained PAT: Contents read/write на `cla-signatures`; + Members read организации для варианта C | подписи (+ членство) |
| `CLA_ENABLED` | переменная организации или репозитория | — | включатель/выключатель |

Права job в новом переиспользуемом workflow и в вызывающих:

| Право | Lite сейчас | `pyrlyn/cla` | Зачем |
| --- | --- | --- | --- |
| `contents` | read | read | чтение PR через API |
| `pull-requests` | write | write | закреплённый комментарий, блокировка/разблокировка |
| `statuses` | write | write | commit status `pyrlyn/cla` |
| `actions` | write | **нет** | перезапусков больше нет |

На тарифе Free секреты организации доступны только публичным репозиториям; все целевые
репозитории публичные.

2. Выключить: удалить `CLA_ENABLED` или задать любое значение, кроме `true`; job пропускается.
3. Код: откатить PR в infra из 5.4 (вернуться к Lite) или закрепить `pyrlyn/cla` на предыдущем
   релизе. Вызывающие закрепляют infra по SHA, поэтому каждый из них меняется, только когда
   меняется его закрепление.
4. `pyrlyn/cla-signatures` не трогать; подписи — юридические записи и никогда не удаляются.

Порядок важен: всегда 1 до 2, иначе PR будут ждать статус, который никогда не придёт.
