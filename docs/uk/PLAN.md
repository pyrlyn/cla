# pyrlyn/cla: план

Статус: план, нічого ще не реалізовано. Написано 2026-10-03.
Це переклад. Джерело істини — англійський [`PLAN.md`](../../PLAN.md); у разі розбіжностей діє
англійський текст. Інші переклади: [російський](../ru/PLAN.md).

`pyrlyn/cla` — невеликий GitHub Action, що належить організації та перевіряє в pull request'ах
підписання Contributor License Agreement (ліцензійної угоди учасника, далі CLA) pyrlyn. Він
замінить CLA Assistant Lite (`contributor-assistant/github-action`), який зараз обгортає
`pyrlyn/infra` і який було архівовано 2026-03-23.

## 0. Цілі та що не входить у задачу

Цілі:

1. Кожен, чия робота є в pull request, «покритий»: підписав поточну версію CLA, є учасником
   організації `pyrlyn` або це бот з allowlist.
2. Підписання, як і раніше, — коментар у pull request з фіксованою фразою, як описано в розділі 11
   `CLA.md`.
3. Один підпис діє для всіх репозиторіїв pyrlyn. Підписи зберігаються в репозиторії, яким
   володіємо ми.
4. Зрозуміла, стабільна обов'язкова перевірка (required check), яку можна вказати в rulesets, і
   один коментар бота, де точно сказано, чого бракує і як це виправити.
5. Версії CLA: нова версія може вимагати підписати угоду знову.
6. Безпека на `pull_request_target`: код із pull request ніколи не checkout'иться і не
   запускається.

Не входить: вебінтерфейс або сторінка «Sign in with GitHub», корпоративні CLA (компанія підписує
за своїх працівників; вирішується зверненням до Ліцензіара, `CLA.md` 11.4), DCO sign-off, інші
платформи, крім GitHub.

## 1. Що існує зараз (дослідження)

Для плану вивчено дві кодові бази:

- **Upstream** `contributor-assistant/github-action`, архівований, останній коміт `58daaf8`
  (2026-03-23). `pyrlyn/infra` закріплює тег `v2.6.1` = `ca4a40a7d1004f18d9960b404b97e5f30a505a08`.
  Ліцензія Apache-2.0.
- **Форк** `iainmcgin/cla-github-action`, `v3.2.0` = `0d27e5a16278d4adb6b0c4b92f08ad27b0a21dc8`
  (2026-06-17). Apache-2.0. Відгалузився від `58daaf8`; зміни описано в його `CHANGELOG.md`.

### 1.1 Процес підписання

- Точка входу `src/main.ts`: на події `closed` лише блокує обговорення pull request
  (`lockPullRequest()`); в інших випадках викликає `setupClaCheck()`.
- `src/setupClaCheck.ts`: збирає авторів комітів, прибирає тих, хто в allowlist, читає файл
  підписів, ділить людей на `signed` / `notSigned` / `unknown` (немає акаунта GitHub), оновлює
  коментар бота, записує нові підписи, а потім або валить job, або перезапускає останній
  невдалий запуск.
- `src/graphql.ts`: автори беруться з GraphQL-запиту `pullRequest.commits`, для кожного коміту
  `author.user`, інакше `committer.user`. Користувач `41898282` (`github-actions[bot]`)
  відкидається завжди. Upstream читає лише перші 100 комітів (без пагінації).
- `src/pullrequest/signatureComment.ts`: отримує коментарі pull request і вважає коментар
  підписом, якщо він збігається з фразою. Upstream використовує нестрогий регулярний вираз
  `^.*i have read the cla document and i hereby sign the cla.*$` для тексту в нижньому регістрі й
  читає лише перші 30 коментарів (без пагінації). Для кожного, хто підписав, зберігаються `name`,
  `id`, `comment_id`, `created_at`, `repoId`, `pullRequestNo`. Коментарі `github-actions[bot]`
  ніколи не зараховуються.
- `src/shared/pr-sign-comment.ts`: фраза за замовчуванням
  `I have read the CLA Document and I hereby sign the CLA` (input `custom-pr-sign-comment`).
- `src/pullrequest/pullRequestComment.ts` + `pullRequestCommentContent.ts`: бот створює один
  коментар і далі редагує його на місці; у ньому список тих, хто не підписав, і фраза, яку треба
  опублікувати.
- Повторна перевірка: workflow, що викликає action, фільтрує події `issue_comment`, тож запуск
  починають лише `recheck` або сама фраза.
- `src/pullRerunRunner.ts`: запуск за коментарем відбувається на події `issue_comment`, тому його
  результат не прив'язаний до head-коміту pull request. Тож action шукає власний workflow **за
  назвою** (`context.workflow`), отримує запуски `pull_request_target` на head-гілці й
  перезапускає останній, якщо той упав. Для цього потрібне `actions: write`; механізм ламається,
  коли два workflow мають однакову назву («Unable to locate this workflow's ID»), і зіставляє
  head-гілку лише за назвою (гілка форку з назвою `main` може збігтися з чужими запусками).

### 1.2 Зберігання

- `src/persistence/persistence.ts`: один JSON-файл `{"signedContributors": [...]}`, який
  читається і записується через contents API (`repos.getContent` / `createOrUpdateFileContents`)
  у гілці з input `branch` за шляхом `path-to-signatures`.
- Той самий репозиторій: використовується `GITHUB_TOKEN`, тому job потрібне `contents: write`, а
  гілка не повинна бути захищеною. Віддалений репозиторій (`remote-organization-name` /
  `remote-repository-name`): використовується `PERSONAL_ACCESS_TOKEN` (`src/octokit.ts`); без
  нього запуск падає з «Please add a personal access token».
- Запис використовує `sha` файлу, отриманий під час читання; два підписи в одну мить конфліктують,
  і один із запусків падає («Could not update the JSON file»). Повтору немає.
- Помилка в upstream: `src/setupClaCheck.ts` порівнює `error.status === "404"` (рядок) з числовим
  статусом, тому гілка «створити файл під час першого запуску» ніколи не виконується. З `v2.6.1`
  відсутній `cla.json` закінчується помилкою «Could not retrieve repository contents. Status:
  404». У форку це виправлено (`c5254b2`). У `pyrlyn/infra` `docs/cla.md` зараз написано, що
  action створює файл сам; із закріпленою версією це не так.

### 1.3 Логіка перевірки

- Результат = результат job: `core.setFailed()` робить job червоним. Statuses API ніде не
  викликається, хоча в задокументованих правах є `statuses: write`.
- Allowlist (`src/checkAllowList.ts`): логіни через кому, шаблон `*` перетворюється на регулярний
  вираз. Upstream перевіряє лише логін; форк перевіряє ще й email коміту (`73f6929`).
- Блокування pull request (`src/pullrequest/pullRequestLock.ts`): після `closed` обговорення
  блокується, щоб коментарі-підписи не можна було відредагувати. Upstream блокує за **будь-якого**
  закриття, зокрема без merge; повторно відкритий pull request тоді не може отримати коментар
  бота. Виправлено у форку `v3.1.0` (`30dab6b`): блокувати лише після merge, розблоковувати при
  `reopened`.
- Ідентичність: поля автора в git не автентифіковані. Будь-хто може створити коміти з чужим email
  (наприклад, бота з allowlist або учасника, який уже підписав); GitHub зіставить email з цим
  акаунтом, і upstream зарахує цей акаунт. Форк у `v3.0.0` додає до перевірюваних людей автора
  pull request і трейлери `Co-authored-by:` (`src/shared/coAuthors.ts`) та падає, коли автор pull
  request не є автором жодного коміту (`require-opener-as-author`, за замовчуванням `true`).
- Форк `v3.2.0` (`1f440bd`): фраза має стояти в окремому рядку, регістр не важливий, `.`/`!` у
  кінці ігноруються, цитовані (`>`) рядки не зараховуються, дозволено зовсім небагато
  додаткового тексту.
- Середовище виконання: `action.yml` upstream оголошує `node20`, форк — `node24`. GitHub запускає
  JavaScript actions на Node 24 з 2026-09-23.

### 1.4 Безпека `pull_request_target`

Обидва проєкти документують зв'язку `pull_request_target` + `issue_comment`.
`pull_request_target` запускає workflow з **базової** гілки з токеном на запис і секретами,
зокрема для pull request'ів із форків. Це безпечно, лише поки workflow ніколи не checkout'ить і не
виконує код із pull request і ніколи не підставляє контрольований зловмисником текст (заголовки,
описи, коментарі, назви гілок) у скрипти `run:`. Жоден із двох actions код не checkout'ить; обидва
читають дані pull request лише через API.

переносити код).

## 2. Вимоги pyrlyn

### 2.1 Хто вважається покритим

Людина покрита, якщо виконується будь-яка з умов; перевіряються в такому порядку:

1. **Учасник організації** `pyrlyn` (проходить автоматично, без підпису). Input
   `members-pass: true`.
2. **Бот з allowlist**, зіставлення за числовим ID користувача та логіном, ніколи за email.
3. **Підписав** версію CLA, яка вимагається зараз.

Перевіряються: автор pull request, кожен автор коміту, кожен комітер, який є користувачем GitHub,
крім `web-flow` (ID `19864447`), і кожен трейлер `Co-authored-by:`. Email автора, не прив'язаний до
акаунта GitHub, вважається «невідомим»: підписати з ним не можна, перевірка залишається червоною, а
коментар пояснює, як прив'язати email або переписати коміти.

Захист від підміни (з форку): якщо автор pull request не є автором чи співавтором жодного коміту,
перевірка падає, якщо тільки він не учасник організації. Тож стороння людина не зможе пройти
перевірку, приписавши коміти боту з allowlist або тому, хто вже підписав.

Юридичне зауваження для Івана: зараз єдиний учасник — `listepo` (правовласник). Майбутній
учасник, який не є Іваном, робитиме внески без підпису. Або учасники підписують окрему угоду, або
ставимо `members-pass: false`. Членство перевіряється в момент перевірки й не зберігається.

### 2.2 Перевірка членства

`GITHUB_TOKEN` не бачить приховане (private) членство в організації: це installation token без
організаційного права «Members». Тоді `GET /orgs/pyrlyn/members/{user}` показує прихованих
учасників як не учасників. Зараз `listepo` — прихований учасник (`/orgs/pyrlyn/public_members`
порожній). `author_association` у даних події теж не надійна ознака членства.

| Варіант | Як | Переваги | Недоліки |
| --- | --- | --- | --- |
| A. **GitHub App** `pyrlyn-cla` (рекомендовано) | застосунок організації, право організації **Members: read**, право репозиторію **Contents: read and write**, встановлений лише на `pyrlyn/cla-signatures`; токен випускається на кожен запуск через `actions/create-github-app-token` | один обліковий запис і для членства, і для зберігання; без терміну дії; доступ до одного репозиторію; коміти підписів від імені бота | треба створити й установити застосунок; два секрети (`CLA_APP_ID`, `CLA_APP_PRIVATE_KEY`) |
| B. Публічне членство | кожен учасник робить членство публічним; перевірка `GET /orgs/pyrlyn/public_members/{user}` з `GITHUB_TOKEN` | для цієї частини не потрібен секрет | залежить від кожного учасника; того, хто приховав членство, попросять підписати |
| C. PAT організації | fine-grained PAT, власник ресурсу `pyrlyn`, право організації **Members: read** (+ Contents на `cla-signatures`) | швидко | прив'язаний до акаунта Івана, спливає, треба замінювати |
| D. Статичний список | учасників перелічено в `allowlist` | без виклику API | застаріває; по суті той самий allowlist |

План: реалізувати A, підтримати C через той самий input (підійде будь-який токен з таким
доступом), B залишити запасним варіантом, якщо токен не передано. Якщо членство прочитати не
вдається (403 / немає токена), людина вважається не учасником, а в коментарі сказано, що
членство перевірити не вдалося. У разі помилки перевірка ніколи мовчки не проходить.

### 2.3 Allowlist ботів

Список за замовчуванням, за логіном; числовий ID визначається під час запуску й порівнюється:

- `dependabot[bot]` (`49699333`), `github-actions[bot]` (`41898282`), `renovate[bot]`.
- Бот застосунку `pyrlyn-cla` і будь-які інші застосунки pyrlyn, додані пізніше.

Шаблони дозволені лише для логінів, що закінчуються на `[bot]`, і задаються явно. Боти не
підписують. Бот покритий лише як автор коміту; бот з allowlist у ролі автора pull request зі
сторонніми авторами комітів цих авторів не покриває.

### 2.4 Текст CLA і версії

- Текст: `pyrlyn/infra` `CLA.md` «Version 1.0 (draft)» (англійський, канонічний) і `CLA.ru.md`
  (російський переклад). Розділ 11 описує підписання фразою
  `I have read the CLA Document and I hereby sign the CLA`, дані, що зберігаються (логін, числовий
  ID, ID і час коментаря, репозиторій і pull request), і те, що один підпис діє для всіх проєктів.
  Розділ 12.2: нова версія застосовується до внесків, зроблених після того, як учасник її прийняв.
- До запуску в п. 11.1 `CLA.md` і `CLA.ru.md` треба прибрати згадку «CLA Assistant Lite»
  (достатньо «автоматична перевірка»). Текст іще чернетка, тож нова версія не потрібна.
  Опційно: український переклад `CLA.uk.md` (його немає).
- Inputs версії: `cla-version` (наприклад, `1.0`), `document-url`, закріплений на коміті
  `pyrlyn/infra` (`.../blob/<sha>/CLA.md`), і `document-sha256` (SHA-256 цього файлу). Action
  зберігає всі три значення в кожному підписі.
- Повторне підписання: input `minimum-version`. Підпис із нижчою версією людину не покриває;
  коментар пише «ви підписали версію X, тепер потрібна версія Y» з посиланням на новий текст.
  Підвищення `minimum-version` — свідомий крок. Сама по собі нова версія (12.2) не робить старі
  підписи недійсними для старих внесків.
- Фраза залишається такою, як у 11.1. Версія — та, на яку посилався коментар бота в момент
  підписання (11.2: «версія, посилання на яку наведено в повідомленні перевірки»).

### 2.5 Повідомлення в pull request

Один закріплений коментар, який знаходиться за прихованою міткою `<!-- pyrlyn-cla -->`,
створюється один раз і потім редагується. Англійською, з посиланнями на `CLA.md` і `CLA.ru.md`.
Містить:

- Таблицю всіх перевірених: логін, причина (учасник / бот / підписав v1.0 такого-то числа / немає
  підпису / невідомий email / застаріла версія).
- Точну фразу в блоці коду та вказівку «опублікуйте її окремим новим коментарем».
- Підказку про `recheck`; інструкцію для неприв'язаного email; попередження про підміну автора,
  якщо воно застосовне.
- Коли всі покриті: один короткий рядок без `@`-згадок.

Commit status (context `pyrlyn/cla`), `description` до 140 символів (тексти англійською, як вони
будуть видні в GitHub):

- `success`: `All 3 contributors covered (1 member, 1 bot, 1 signed CLA 1.0)`
- `failure`: `CLA 1.0 signature missing: @alice, @bob. See the pull request comment.`
- `failure`: `Unknown commit email (not linked to GitHub): 1. See the comment.`
- `failure`: `PR opener @mallory is not an author of any commit.`
- `error`: `CLA check could not read signatures (HTTP 403). Maintainers: see the run log.`

`target_url` веде на коментар бота. Job пише step summary з тією самою таблицею.

## 3. Структура

### 3.1 Структура репозиторію

```
action.yml            name, inputs, outputs; runs.using: node24, main: dist/index.js
src/main.ts           маршрутизація подій: pull_request_target, issue_comment, closed, reopened
src/config.ts         inputs, перевірка (одразу падати за неправильної конфігурації)
src/people.ts         автор PR, автори, комітери, Co-authored-by (GraphQL з пагінацією)
src/membership.ts     членство в організації, кеш на час запуску
src/allowlist.ts      боти за ID і логіном
src/signing.ts        зіставлення фрази (строго, окремий рядок, без цитат)
src/store.ts          файл підписів: читання, додавання, запис із повтором при 409
src/report.ts         закріплений коментар, commit status, step summary
src/lock.ts           блокування після merge, розблокування при reopen
tests/unit/           vitest, по файлу на модуль
tests/integration/    цілі запуски проти підробленого GitHub (записані payload'и, msw)
dist/index.js         бандл (ncc або esbuild), комітиться; CI падає, якщо він застарів
.github/workflows/    ci.yml (lint, typecheck, test, перевірка dist), release.yml
NOTICE, LICENSE, README.md, PLAN.md, docs/ru, docs/uk
```

Node 24, TypeScript, `@actions/core`, `@actions/github`, `@octokit/plugin-retry`. Під час
виконання жодних мережевих звернень, крім GitHub API.

### 3.2 Inputs (перша версія)

`github-token` (за замовчуванням `github.token`; коментар, статус, блокування), `cla-token`
(підписи + членство; токен застосунку або PAT), `org` (`pyrlyn`), `members-pass` (`true`),
`allowlist`, `signatures-repository` (`pyrlyn/cla-signatures`), `signatures-branch` (`main`),
`signatures-path` (`signatures/cla.json`), `document-url`, `document-url-ru`, `cla-version`,
`document-sha256`, `minimum-version`, `sign-phrase`, `status-context` (`pyrlyn/cla`),
`lock-after-merge` (`true`), `require-opener-as-author` (`true`).
Outputs: `covered` (`true`/`false`), `missing` (JSON-список логінів).

### 3.3 Файл підписів

```json
{
  "schema": 1,
  "signatures": [
    {
      "user": "alice", "user_id": 123,
      "cla_version": "1.0", "document_sha256": "…",
      "signed_at": "2026-10-10T12:00:00Z",
      "comment_id": 456, "comment_url": "https://github.com/pyrlyn/cox/pull/1#issuecomment-456",
      "repository": "pyrlyn/cox", "repository_id": 789, "pull_request": 1
    }
  ]
}
```

Лише додавання; зіставлення за `user_id`, ніколи за логіном (логін можна перейменувати). Запис:
прочитати, додати, записати з прочитаним `sha`, при 409 перечитати й повторити (до 5 разів).
Відсутній файл створюється. Підписів поки немає, тож міграція формату Lite не потрібна.

### 3.4 Зберігання: окремий репозиторій чи гілка

| | `pyrlyn/cla-signatures` (приватний) | гілка в тому самому репозиторії |
| --- | --- | --- |
| Токен | запис в один приватний репозиторій | `contents: write` на репозиторій із кодом |
| Історія | окрема, не засмічує закріплення коду | коміти підписів у кожному репозиторії |
| Один підпис на всі репозиторії | так | ні (по файлу на репозиторій) |
| Захист гілок | незахищена лише `main` там | незахищена гілка в кожному репозиторії з кодом |

Рішення: `pyrlyn/cla-signatures`. Він уже існує (приватний, створений 2026-10-02) і **порожній**:
GitHub відповідає 409 «Git Repository is empty», тому потрібен перший коміт (README), перш ніж
contents API зможе в нього писати. Робити резервні копії (наприклад, щотижневий
`git clone --mirror`).

### 3.5 Події та workflow для повторного використання

Action залишається кроком усередині наявного reusable workflow `pyrlyn/infra`
`.github/workflows/cla.yml`; репозиторії, що його викликають, зберігають свій тонкий `cla.yml`:

- `pull_request_target`: `opened`, `synchronize`, `reopened`, `closed`.
- `issue_comment`: `created`, лише для pull request'ів, коли текст містить фразу або дорівнює
  `recheck`.
- Запуск за коментарем сам ставить commit status на **head SHA** pull request. Це прибирає логіку
  перезапуску, `actions: write` і правило «назва workflow має бути унікальною».
- Concurrency: `group: cla-${{ github.event.pull_request.number || github.event.issue.number }}`,
  `cancel-in-progress: false`.
- Ніколи `actions/checkout`, ніколи не запускати `npm`/скрипти з pull request, жодних `${{ … }}` з
  текстом події всередині `run:`. Action лише викликає API.
- Вимикач `vars.CLA_ENABLED == 'true'` залишається.

Job зелений, якщо action відпрацював; рішення — це commit status. Червоний job означає, що впав сам
action; тоді статус не ставиться, і обов'язкова перевірка блокує merge (fail closed).

### 3.6 Назва обов'язкової перевірки

Rulesets вимагають status context **`pyrlyn/cla`** (а не назву job `cla / cla`). Його ставить
застосунок `github-actions`; у ruleset можна закріпити це джерело (integration ID `15368`).

### 3.7 Релізи та закріплення

- Семантичні версії `v1.0.0`, …, підписані анотовані теги, GitHub releases з описом. Плаваючий
  тег `v1` — лише для зручності.
- Споживачі закріплюють повний SHA коміту з коментарем `# v1.0.0` (як `pyrlyn/infra` уже робить
  для всіх actions; це перевіряє `action-pins.yml` в `infra`).
- CI на кожен PR: lint, typecheck, тести, актуальність dist. Релізи лише з `main`.
- Dependabot для npm і actions у `pyrlyn/cla`; Dependabot у `pyrlyn/infra` оновлює закріплення.

## 4. Секрети та права

Поточний стан (перевірено 2026-10-03): `gh secret list -o pyrlyn` показує `CARGO_REGISTRY_TOKEN`,
`MACOS_CERTIFICATE`, `MACOS_CERTIFICATE_PWD`, `RELEASE_PLZ_TOKEN`. **`CLA_SIGNATURES_TOKEN` не
існує.** Змінних організації немає, тобто `CLA_ENABLED` на рівні організації не задано.

| Облікові дані | Де | Доступ | Для чого |
| --- | --- | --- | --- |
| `github.token` | кожен запуск | права job нижче | коментар бота, commit status, блокування/розблокування, читання PR |
| `CLA_APP_ID`, `CLA_APP_PRIVATE_KEY` (варіант A) | секрети організації, вибрані репозиторії | застосунок: Members read на рівні організації; Contents read/write лише на `cla-signatures` | членство, підписи |
| `CLA_SIGNATURES_TOKEN` (варіант C або старий Lite) | секрет організації, вибрані репозиторії | fine-grained PAT: Contents read/write на `cla-signatures`; + Members read організації для варіанта C | підписи (+ членство) |
| `CLA_ENABLED` | змінна організації або репозиторію | — | вмикач/вимикач |

Права job у новому reusable workflow і в тих, хто його викликає:

| Право | Lite зараз | `pyrlyn/cla` | Навіщо |
| --- | --- | --- | --- |
| `contents` | read | read | читання PR через API |
| `pull-requests` | write | write | закріплений коментар, блокування/розблокування |
| `statuses` | write | write | commit status `pyrlyn/cla` |
| `actions` | write | **немає** | перезапусків більше немає |

На тарифі Free секрети організації доступні лише публічним репозиторіям; усі цільові репозиторії
публічні.
